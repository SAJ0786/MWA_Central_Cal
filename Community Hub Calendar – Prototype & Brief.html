1. Overview

A single, shared calendar that is the source of truth for every event, hire and programme run by the organisation. Departments (Event Organisers, Private Hire Booking, Local Events, Community Programs) check availability and submit bookings themselves; a central team approves. The prototype above is a working front end with in-browser data; the build should be API-first so the future website and mobile app consume the same data.

2. Problem & goals

Problem: Teams coordinate by email, phone and separate spreadsheets, causing double-bookings, slow confirmation and no single view of venue usage.

  • Eliminate double-bookings through automatic conflict checking per venue.
  • Cut manual coordination: self-service booking with an approval step.
  • One data source that feeds the public website, app and internal reporting.

4. MVP scope

  • Month / week / day calendar, filter by department and venue
  • Create, edit, cancel bookings; overlap detection per venue
  • Status workflow: Pending → Confirmed / Rejected / Cancelled
  • Email notifications on submit and decision
  • Role-based login; audit log of changes
  • Public/private visibility flag per event
  • Hijri (Islamic) calendar alongside Gregorian: dual dates, Hijri-based events, moon-sighting day adjustment
  • iCal (.ics) feed and CSV export

Out of scope (MVP): payments/invoicing, ticketing, recurring-series exceptions, resource inventory (chairs, AV) – planned for Phase 3.

6. Integration-ready design

  • REST API (JSON, OpenAPI documented), versioned /v1; token auth per app.
  • Webhooks on create/update/status change so website, CRM or messaging can react.
  • Embeddable widget and public read-only endpoint for the website.
  • iCal feeds per department and venue for Google/Outlook.
  • Store all times in UTC with organisation timezone (Australia/Sydney) for display.

6a. Hijri calendar support

  • Canonical storage: every event keeps a resolved Gregorian start/end (UTC), so conflict checks, iCal and integrations stay simple. Hijri-based events also keep their source hijriDate and are re-resolved whenever the adjustment changes.
  • Dual display: Gregorian and Hijri dates shown together in the calendar, lists and emails, with a per-user toggle. The month header shows the Hijri month range.
  • Entering dates: choose Gregorian or Hijri when booking, with a live conversion preview.
  • Moon-sighting adjustment: many communities start months by sighting, so calculated dates can differ by 1–2 days. Admins set the adjustment (ideally per Hijri month), it is audit-logged, and affected organisers are notified when a booking moves.
  • Recurrence: yearly (e.g. annual commemorations) and monthly events on a Hijri day.
  • API: events return both dates, e.g. "date":"2026-10-13","hijri":{"day":1,"month":5,"monthName":"Jumada I","year":1448}, and can be filtered with hijriMonth / hijriYear. iCal export uses Gregorian dates.
  • Consistency: reuse the same Hijri conversion logic as the Community Events App (extract it into a shared module) so both products always agree.

Prototype note: it uses the browser's built-in tabular (civil) Islamic calendar plus a global ±2 day adjustment. Production should use the authoritative method confirmed in discovery.

7. Suggested technology

React + TypeScript front end (PWA) with a Firebase backend (Auth, Firestore, Cloud Functions for conflict checks, notifications and the REST layer). Conflict checks must be enforced server-side in a transaction, not just in the UI. Alternative: Postgres (Supabase) if reporting needs grow.

9. Success measures

  • Zero double-bookings after go-live
  • Booking-to-confirmation time reduced by 50%+
  • All departments booking through the tool within 3 months
  • Reduction in coordination emails/calls (baseline survey in Phase 0)

10. Risks & open questions

  • Adoption: teams keep using spreadsheets – mitigate with training and a cut-over date.
  • Approval rules differ per department – confirm in discovery.
  • Privacy: private hire details must not appear in public feeds.
  • Open: Which Hijri method is authoritative, and who announces the moon-sighting adjustment? Do hires need buffers for setup/pack-down? Who owns final approval? Are there fees per venue? Do existing bookings need migrating?
